# Admin CRM and profile media · decision requested

**UNAPPLIED / PROPOSED.** This specification sits outside the migration runner. It requests staging authority only. Baseline `4f26f4f56fd0f3e80f00386f034c54837bd82d34`. Treat existing requests, profile images, admin access and publication as authoritative. Never populate example records in either hosted environment as part of this proposal.

## Existing dependencies

Reuse `lead_requests.id/status/created_at/updated_at`, `farmers.id/updated_at`, `suppliers.id/updated_at`, existing registration links, and existing private staff authentication. Buyer delivery date remains `lead_requests.required_by`. A staff follow-up uses a separate timestamp. Do not link historic requests by phone, WhatsApp number, company name or similarity. An existing “Contacted” status is not proof of a first reply. No backfill is proposed. Absence of historical evidence must remain “unverified” for pre-cutover cases, even if staff have recorded no new events.

## Exact proposed objects

Use an unexposed schema `staff_crm`. The column dictionary below is the schema specification. All columns are NOT NULL unless marked `?`. Every UUID referencing a request, profile, identity or Auth user uses ON DELETE RESTRICT. Use UTC `timestamptz` and database-generated time. Keep the operational audit append-only. Do not copy contact numbers into it.

**Event constraints.** Allowed kinds are `claim`, `handover`, `follow_up_completed`, `buyer_contact`, `seller_contact`, `status`, `link`, `unlink`. Contact requires an explicit human confirmation, a real event time no later than now and no earlier than intake, plus channel `whatsapp|phone|email|other`. Seller contact has exactly one verified farmer/supplier reference and never sets first_buyer_reply. Buyer contact has neither seller reference. First reply is set only on the first qualifying buyer-contact command. Do not count a launch of an external app, copy, claim, private note or seller conversation. Case-insensitive keys and arbitrary JSON are not accepted: each kind has a fixed input shape, rejects unknown fields and caps a note/action/reason at 2,000/300/300 characters respectively.

## Functions and concurrent behaviour

All signatures below are proposed; no callable endpoint exists today. Return typed JSON envelopes with an explicit result, case/job ID and saved version. Exposed RPCs live in `public` so the existing server-only Data API client can call them without exposing the private schema. Functions use fixed empty search_path, schema-qualified names, no dynamic SQL. Use a dedicated non-login function owner with only required table grants; run read and write functions SECURITY DEFINER. Revoke EXECUTE from PUBLIC, anon and authenticated at creation, grant only service_role. No direct browser RPC and no new staff role. The server verifies the existing admin session for every request, sets the actor from the verified session and never accepts a client-supplied actor. Staging must prove ordinary users, applicants and users without the existing admin entitlement cannot read or write.

**RLS and grants.** Enable RLS on all six tables. No anon/authenticated policies. Revoke all schema privileges on staff_crm and table privileges on all six from PUBLIC, anon and authenticated. Private tables have no PostgREST exposure or direct API-role grants. Only the designated function owner may select/insert/update the private state it needs; events get SELECT/INSERT only. No DELETE grants. For public.admin_activity_log grant service_role only SELECT/INSERT to keep existing server callers compatible; revoke UPDATE/DELETE from API roles. No changes to auth.users, existing staff privileges, public directory policies or other existing tables. Confirm profile and lead updates inside RPCs use the same server validations as the current protected APIs. Deploy new server routes only after these grants and negative tests pass.

### Exact role and access policy proposal

Create one non-login, non-inheriting, non-superuser, non-BYPASSRLS function role `gg_staff_api`. No membership grant to an app user, anon, authenticated or service_role. Table ownership stays with the migration owner. Revoke direct privileges on new private tables from service_role too (Supabase default grants can be explicit). Private schema USAGE only to the function role and migration owner. Set default grants for newly created functions to deny public execution. Grant USAGE on public to the function owner. Revoke EXECUTE on each listed RPC from PUBLIC, anon and authenticated in the same transaction as creation. Grant RPC execution to service_role only. Do not expose staff_crm in Data API settings.

- `cases`, `buyer_links`, `supplier_media_jobs`: grant SELECT, INSERT and UPDATE to gg_staff_api with role-only RLS policies for those commands; no DELETE policy. Use USING (true) for SELECT and UPDATE, WITH CHECK (true) for INSERT and UPDATE; RPCs enforce row ownership/version and verified admin scope.
- `events`, `buyer_identities`: SELECT and INSERT only for gg_staff_api, with matching role-only policies. Never UPDATE or DELETE events. Borrow no SQL privileges from logged-in staff identities.
- Existing tables: the named functions need to read individual request/profile IDs, lead status/updated_at and supplier editable fields and write only existing approved columns. Do not widen any current public or authenticated grants. A new definer role cannot implicitly cross existing RLS. Before staging SQL, inspect actual policies and owner permissions: either use the existing service-only, authenticated admin server to carry out existing reads, or propose explicit SELECT/UPDATE policies **only for gg_staff_api** on public.lead_requests and public.suppliers. Exact proposed policy if needed: `gg_staff_crm_read` FOR SELECT TO gg_staff_api USING(true), `gg_staff_crm_update` FOR UPDATE TO gg_staff_api USING(true) WITH CHECK(true), only on these two tables. Pair with column grants for lead `id,created_at,updated_at,status` (UPDATE status only); supplier SELECT `id,updated_at` and the released supplier editable columns, UPDATE only the editable columns validated by the same server rules. Row locks require UPDATE privilege. No INSERT/DELETE on existing records. Review these two scoped policies explicitly before any execution.
- Eligible actors and handover recipients must use the existing trusted admin authorization policy. For an RPC receiving an actor from a trusted server, the server must also verify any nominated owner is a current staff admin. Never return a directory of Auth users to browsers or grant SELECT on auth.users merely to resolve an owner.
- `admin_activity_log`: legacy service_role SELECT and INSERT only. No public/ordinary role policy. Preserve any genuine historic rows and the complete released action/entity enum. For an already-existing table with other dependencies, stop before altering its definition.
- A retry lease with null job ID locks the oldest eligible pending/expired job via FOR UPDATE SKIP LOCKED; this permits recovery after a worker restart without direct table access. Scope the result to its own lease. A stale/expired worker cannot attach or delete another lease's winning object. No new hosted queue, cron or external service is proposed.
- Set a reviewed UTC cutover timestamp as versioned application configuration for the first-reply evidence horizon. For older leads, absence of qualifying evidence is “historical reply unverified”, not an overdue claim. Separately decide whether staff may confirm a known historic reply with evidence. No backfill.

## Storage and holiday coverage

**Farmer media:** No database, bucket or policy changes proposed. Continue the existing private farmer-application-media editor-staging area and public farmers/editor-uploads area. New save attempts have unique public object names. Compare byte digests, CAS by loaded profile updated_at, and remove only the losing attempt’s own public copy on definite conflict. Keep the private draft on failed Save. On uncertain outcome retain both, read back before any cleanup. Existing approved application originals and existing live assets stay intact.

**Supplier media:** Reuse the existing private supplier-application-media bucket and public suppliers bucket. Proposed new object keys (not created): `editor-staging/<supplier_uuid>/<operation_uuid>.<ext>` privately; `editor-uploads/<supplier_uuid>/<field>/<operation_uuid>.<ext>` publicly. Staging and signed previews (10 minutes) restricted to the existing server-authorised staff flow. Proposed Storage policy delta: **none** if catalog and negative download/list/write tests confirm existing private bucket and service-only writes; stop and present a specific policy delta otherwise. Never change bucket visibility. Image picking alone does not write publicly. Original private registration assets are copied into private editor staging via the linked, reviewed application, never moved. Record durable Save before a public copy; until attach, use the old profile URL. Private originals from registration are excluded from all cleanup. For abandoned editor drafts, expire only verified unreferenced keys after a 24-hour grace period. Only delete a losing public key if the job conclusively lost and no current profile or active job references it. Retain uncertain copies for reconciliation. Public buckets can expose by known URL after committed Save and before attach; this design does not promise a private ACL on public bucket objects.

**Ghana business days:** Use a versioned offline repository calendar, with coverage start/end, public notice URL, observed date and last verified date. Require founder/staff ownership of updates and verify official substituted and one-off days. Unknown coverage yields “unavailable.” No runtime holiday service, database table or environment change proposed. Received date is day zero; the next open day is day one, including after-close and weekend receipts. Remind at 09:00 GMT day one, overdue strictly after 17:00 GMT day two. [Ghana Ministry of the Interior calendar](https://mint.gov.gh/documents/statutory-holidays-commemorative-days-in-the-republic-of-ghana-for-the-year-2026/)
